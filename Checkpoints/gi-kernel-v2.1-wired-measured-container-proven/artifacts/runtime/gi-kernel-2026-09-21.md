## §6 · THE RUNTIME LEDGER — what RUNNING taught that READING could not
1. **The schema is already the six-layer schema.** `kind` (node type) · `predicate`
   (edge type) · `evidence_quote` (provenance) · `confidence` (score) ·
   `created_run`/`superseded_run` (versioning). Reading the code I thought these were
   v2.0 additions. They are live, on 3,980 rows, today.
2. **`superseded_run` + `uq_tn_live_canonical` is already an RSI substrate.** Live = one
   row per canonical id; updating = supersede old + insert new. The self-improvement
   mechanism does not need to be invented. It needs to be USED.
3. **The store is per-project-root and per-session, and sessions never populate.** So the
   gate on a live session reads NOTHING. That is why `grep typed_nodes` in the gate = 0
   hits — there is nothing to read at a live session's path.
4. **The gate reads no store AND persists no state.** Both halves of the v1.3 store story
   are inert on the live path.
5. **A stale graph is indistinguishable from a fresh one** — one field (`populated_at`)
   exists but nothing compares it to anything.
6. **`confidence` is the field v2.0's bands depend on, and it is a constant.** Any design
   that gates on confidence gates on 1.0 forever.
